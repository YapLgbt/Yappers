# Deleting a post or reply

Transport v5 uses Iroh ALPN `yappers/netkit/5`. New posts, replies, votes and deletes use event version 4. A public-home upgrade requires the server, its peers, standby and clients to move together. A populated old feed cannot acquire new author signatures. Use fresh data paths for the prelaunch cutover. Existing home and account signing keys can be preserved. This release does not erase files left by a previous deployment.

## What a peer verifies

The creation event contains a random 32-byte nonce and a complete typed action. For a post or reply the signer hashes the 32 decoded nonce bytes followed by the canonical Rust JSON encoding of the action with BLAKE3 derive-key context `yap content commitment v4`. This covers the headline, text, byline, profile, thumbnail, location and reply parent when present. The permanent payload substitutes an empty nonce and an `erased` action containing the commitment and a boolean indicating a reply. The event ID hashes the permanent payload under `yap:event:v4\0`. The device signs the ID under `yap:author:v4\0`. Votes and deletes keep their complete action in the permanent payload. Receiving a live post requires recomputing the commitment and validating the opening. The salt is twice the 128-bit minimum recommended for selective disclosure in [RFC 9901 §9.3](https://www.rfc-editor.org/rfc/rfc9901.html#section-9.3).

The home attests to the event ID, originating home and acceptance time. For portable accounts it checks the supplied account chain and requires the current revision to authorize the signing device. The signed event retains the root-signed grant used at acceptance. After rotation, the replacement device can delete a post created by a previously authorized device. Peers verify both signatures, both grants, both home receipts, the target ID, community and account ownership. They rely on the accepting home's knowledge of revocation at acceptance. An isolated home can lack a newer account revision. A peer inspecting a deleted header can verify these facts without inspecting the former content. Account identifiers, community, timing, sequence and commitments remain linkable metadata.

An erased event travels with the complete signed deletion envelope, even on the first page of a new peer's initial sync. Checking the proof includes checking its originating home's admission for the community. The home reserves a deletion slot for each live post and reply within its event-count limit. A delayed full event, private-history upload or repeated submission cannot replace a matching deletion. A local hide and an account block have no authority to erase someone else's post. Independent readers can retain material they already received.

## Storage and backup

The active home overwrites the envelope with the header and proof and clears derived bylines and cached feed projections. Photos and approximate locations are fields of the erasable action. There is no separate post attachment store or full-text index. SQLite uses secure deletion, file-backed DELETE journals, EXTRA synchronous commits and in-memory temporary storage. A deletion and its key retirement commit together across the data file and its attached guard database. HA workers stage revisions in RAM. The authority clears stale cached responses in the same transaction that commits a deletion. A returning worker must obtain the committed revision before serving. A device or independent home can apply a deletion once it learns of it.

The file next to a standalone database or HA ledger with suffix `.deletion-guard` is live security state. It contains deletion proofs, the current account registry, and keys for recoverable backup content. Protect it with the same private permissions as the home. Keep a **current** guard independently of historical backups. Never retain a point-in-time copy of it with old backups. Losing the guard loses backup access. Rolling **both** the home and guard back defeats rollback protection. A raw copy or host volume snapshot may preserve plaintext, keys, journals or filesystem blocks. Use these commands for historical backups and exclude live data volumes, guard files, temporary exports and process dumps from snapshot retention.

The checked-in Fly mount configuration disables scheduled raw volume snapshots. Verify the setting on the provisioned volume at cutover and account for the expiry of any existing snapshots. [Fly volume snapshot settings](https://fly.io/docs/reference/configuration/#scheduled_snapshots).

- For a standalone home, run `yappers-server backup --database HOME_DB --output NEW_BACKUP`. The command requires an existing initialized home and its matching guard. A missing source fails before archive creation.
- For the HA pair, run `yappers-server ha-export --ledger LEDGER --grant GRANT_JSON --output NEW_BACKUP`.
- With the original authority stopped before cutover, run `yappers-server restore --guard CURRENT_GUARD --input BACKUP --output NEW_HOME_DB`. The output must be a new path. Keep the original guard location accessible. The restored home references that same guard and shares its service lock. Retire the old data volume after verifying the restored home. Its raw files can contain content erased after the cutover. For HA, seed a new authority from the restored standalone database and make a fresh protected backup after the transfer. Successful bootstrap retires the source database and its backup keys.

Managed backups keep an encrypted SQLite image. Inside it, each content opening is independently encrypted with XChaCha20-Poly1305 and a fresh random nonce. The per-event key lives only in the guard. Backup construction discards public feed caches and compacts the temporary in-memory image before serialization. Erasure removes the applicable keys and retains signed deletion evidence. Restoring an older backup recovers surviving content, applies later known deletions and account revisions, verifies envelopes, and only then publishes the restored file. The guard epoch rejects a stale raw database. This guarantee depends on the current guard and the storage operator's handling of historical media. SQLite secure deletion has limits on physical storage and virtual tables. [SQLite secure deletion](https://www.sqlite.org/pragma.html#pragma_secure_delete) and [atomic attached database transactions](https://www.sqlite.org/lang_attach.html).

Account recovery files exported by users are independently controlled copies. A home cannot revoke their passphrase or recall screenshots, copies on offline devices, or data retained by another operator. Import into a home that already knows a deletion preserves it.

## Release verification

Run `cargo test --locked --workspace` for verification, cold-peer and returning-peer replication, stale uploads, device rotation, backup restore and HA crash/failback. Run `scripts/build-web.sh` with the matching wasm-bindgen CLI and `scripts/test-web.sh` for browser publication and deletion. A single clean cutover is possible before launch. Preserve the existing deployment until the new server, standby, clients and backup/restore procedure have passed those checks. Retiring existing deployment data is a separate operator action.
