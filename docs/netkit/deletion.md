# Deleting content and accounts

Home supports Iroh ALPN `yappers/netkit/7` for multiplexed requests and `yappers/netkit/6` for single-request connections. Posts, replies, votes and deletes use event version 4. The storage upgrade preserves the existing wire format, signing keys and signatures. Stores containing earlier signed event formats require a separate cutover because an operator cannot recreate author signatures.

## What a peer verifies

The creation event contains a random 32-byte nonce and a complete typed action. For a post or reply the signer hashes the 32 decoded nonce bytes followed by the canonical Rust JSON encoding of the action with BLAKE3 derive-key context `yap content commitment v4`. This covers the headline, text, byline, profile, thumbnail, location and reply parent when present. The permanent payload substitutes an empty nonce and an `erased` action containing the commitment and a boolean indicating a reply. The event ID hashes the permanent payload under `yap:event:v4\0`. The device signs the ID under `yap:author:v4\0`. Votes and deletes keep their complete action in the permanent payload. Receiving a live post requires recomputing the commitment and validating the opening. The salt is twice the 128-bit minimum recommended for selective disclosure in [RFC 9901 §9.3](https://www.rfc-editor.org/rfc/rfc9901.html#section-9.3).

The home attests to the event ID, originating home and acceptance time. For portable accounts it checks the supplied account chain and requires the current revision to authorize the signing device. The signed event retains the root-signed grant used at acceptance. After rotation, the replacement device can delete a post created by a previously authorized device. Peers verify both signatures, both grants, both home receipts, the target ID, community and account ownership. They rely on the accepting home's knowledge of revocation at acceptance. An isolated home can lack a newer account revision. A peer inspecting a deleted header can verify these facts without inspecting the former content. Account identifiers, community, timing, sequence and commitments remain linkable metadata.

An erased event travels with the complete signed deletion envelope, even on the first page of a new peer's initial sync. Checking the proof includes checking its originating home's admission for the community. The home reserves a deletion slot for each live post and reply within its event-count limit. A delayed full event, private-history upload or repeated submission cannot replace a matching deletion. A local hide and an account block have no authority to erase someone else's post. Independent readers can retain material they already received.

## Deleting an account from a phone

**Delete account** in the iOS and Android profile settings asks for confirmation, then contacts the account’s Home. The recovery authority signs the deletion intent and a currently authorized device authenticates the request. Home enumerates the account’s live posts and replies across communities, including private authored history. The device signs a deletion for each target in batches. Home also removes the profile, releases the username, clears account-owned messaging and push records, and records the retired account ID in its independent deletion guard. The guard prevents a later registration or managed restore from bringing the account back on this Home. Older protected archives can contain account metadata encrypted under the Home backup key. Restore uses the current guard to purge that metadata before opening the restored database.

The phone saves its place before sending each batch. After Home confirms completion, the app erases the account keys, cached content and drafts on that phone and returns to Welcome. If interrupted, it can retry with the same proofs or finish local cleanup. Previously delivered messages on other devices, independently exported files and separately submitted moderation reports have their own lifetimes.

## Storage and backup

A standalone Home stores its catalog, signed event headers and encrypted post and reply bodies in `HOME_DB.primary.turso`. The configured `HOME_DB` names the primary through a small locator. Each body, reply routing record, named byline and cached public projection item is encrypted under a key derived from the corresponding event’s opening key. The independent `HOME_DB.deletion-guard` holds those opening keys in SQLite with secure deletion, DELETE journals and EXTRA synchronous commits.

When Home accepts a deletion, one Turso transaction attaches the signed proof, removes the live opening and records the deletion for the guard. The guard securely retires the public and private keys covered by that proof and advances its record of the primary's committed history. Home acknowledges the deletion after both steps succeed. If Home exits between them, it applies the committed guard updates before serving again. A primary older than the guard, or one from a different history, fails validation. A device or independent Home can apply a deletion once it learns of it.

The guard also retains current account revisions, delivery history and deletion proofs for protected restore. Losing it loses access to encrypted bodies and managed backups. Keep the guard current. Never retain a point-in-time guard with old backups. Rolling both the Home and guard back defeats rollback protection.

The dedicated host owns the locator, the Turso database and its journal files, and the deletion guard. Exclude the entire live data directory, temporary exports and process dumps from historical snapshot retention. Fly serves static files. Use the protected commands for historical backups.

- For a standalone home, run `yappers-server backup --database HOME_DB --output NEW_BACKUP`. When a Home is running, the CLI requests a consistent export through its local owner socket. The operator invoking the CLI writes the archive. A stopped Home can be backed up directly. A missing source fails before archive creation.
- For the HA pair, run `yappers-server ha-export --ledger LEDGER --grant GRANT_JSON --output NEW_BACKUP`.
- With the original authority stopped before cutover, run `yappers-server restore --guard CURRENT_GUARD --input BACKUP --output NEW_HOME_DB`. The output must be a new path. Keep the original guard location accessible. The restored home references that same guard and shares its service lock. Retire the old data volume after verifying the restored home. Its raw files can contain content erased after the cutover. For HA, seed a new authority from the restored standalone database and make a fresh protected backup after the transfer. Successful bootstrap retires the source database and its backup keys.

Managed backups keep an encrypted SQLite image. Inside it, each content opening is independently encrypted with XChaCha20-Poly1305 and a fresh random nonce. The per-event key lives only in the guard. Backup construction discards public feed caches and compacts the temporary in-memory image before serialization. Erasure removes the applicable keys and retains signed deletion evidence. Restore uses the current guard to recover surviving content and apply later deletions and account revisions in memory. It writes verified surviving bodies to a fresh encrypted Turso file before publishing the restored catalog. The guard epoch rejects a stale raw database. This guarantee depends on the current guard and the storage operator's handling of historical media. SQLite secure deletion has limits on physical storage and virtual tables. [SQLite secure deletion](https://www.sqlite.org/pragma.html#pragma_secure_delete) and [atomic attached database transactions](https://www.sqlite.org/lang_attach.html).

Account recovery files exported by users are independently controlled copies. A home cannot revoke their passphrase or recall screenshots, copies on offline devices, or data retained by another operator. Import into a home that already knows a deletion preserves it.

## Release verification

Run `cargo test --locked --workspace` for verification, cold-peer and returning-peer replication, stale uploads, device rotation, backup restore and HA crash/failback. Run `scripts/build-web.sh` with the matching wasm-bindgen CLI and `scripts/test-web.sh` for browser publication and deletion. A single clean cutover is possible before launch. Preserve the existing deployment until the new server, standby, clients and backup/restore procedure have passed those checks. Retiring existing deployment data is a separate operator action.
